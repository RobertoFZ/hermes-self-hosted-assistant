# Migration safety & authenticity

Migrations are normally out of scope as "generated" — but Django migrations are hand-touchable, so you DO review them for two things: **authenticity** (is it really what it claims) and **safety** (will it lock a big table).

## The blocker rule — heavy-table indexes

**An index added on a large / raw table without `atomic = False` + a concurrent build is a `blocker`** (category `migration_safety`, critical → never approve).

Large/raw tables in `price-engine-python`: **`TripObservation` (~2.08B rows)**, **`FareObservation` (~94 GB)**, **`SeatObservation` (~63 GB)**, and any high-write observation/event table.

A safe heavy-index migration looks like the repo's real `0211_busline_seat_type_index.py`:

```python
from django.contrib.postgres.operations import AddIndexConcurrently
from django.db import migrations, models

class Migration(migrations.Migration):
    atomic = False                                   # <-- required
    dependencies = [("web", "0210_...")]
    operations = [
        migrations.SeparateDatabaseAndState(
            state_operations=[
                migrations.AlterField(               # db_index=True for state only
                    model_name="busline", name="seat_type",
                    field=models.CharField(db_index=True, max_length=255, null=True, blank=True),
                ),
            ],
            database_operations=[
                AddIndexConcurrently(                 # <-- concurrent build, no table lock
                    model_name="busline",
                    index=models.Index(fields=["seat_type"], name="busline_seat_type_index"),
                ),
            ],
        ),
    ]
```

**Flag as `blocker`** when you see any of these on a large/raw table:
- `migrations.AddIndex(...)` or `db_index=True` via a plain `AlterField`/`AddField` that builds the index in-transaction.
- A `Migration` with no `atomic = False` (defaults to `atomic = True`) that creates/alters an index on such a table.
- `AddIndex` / `CreateModel` with indexes on an observation table without `SeparateDatabaseAndState` + `AddIndexConcurrently`.

Comment example (blocking):
> Esta migración agrega un índice sobre `TripObservation` pero corre dentro de transacción (`atomic` por default es `True`). Sobre una tabla de ~2 mil millones de filas, construir el índice así toma un `ACCESS EXCLUSIVE` y bloquea escrituras durante horas, frenando el pipeline. Usa `atomic = False` con `AddIndexConcurrently` (y `SeparateDatabaseAndState` para el estado), como en `0211_busline_seat_type_index.py`.

Small/normal tables don't need `CONCURRENTLY` — only flag this for large/raw/high-write tables.

## Authenticity — calibrated to THIS repo

The spec mentions checking the `# Generated by Django <version> on <date>` legend. **Important calibration:** this repo does **not** use that legend — its migrations carry **hand-written module docstrings** instead (see `0261_strategycoupon_tripfare_raw_price.py`: `"""Add raw price fields to StrategyCoupon and TripFare."""`). That's the accepted house style, so a missing `# Generated by Django` line is **not** a finding here.

What the team actually flags on migrations:
- **AI-generated noise comments.** A ChatGPT/LLM-style generation comment that adds no useful metadata → ask to remove it or keep only the standard Django-generated header. (backend PR 3741: *"Este comentario de generación por ChatGPT no aporta metadata útil y queda fuera del estilo estándar de migraciones. Sugiero eliminarlo o dejar solo el encabezado estándar generado por Django."*) — severity `nit`/`minor`, category `architecture` (not critical).
- **Hand-edited logic posing as a pure schema migration.** A custom `RunPython` data migration with a docstring claiming it's a trivial autogenerated field add, or a drifted/inconsistent date in a header that contradicts a hand edit → flag the mismatch so reviewers know it needs data-migration scrutiny. Category `correctness` if the `RunPython` has a logic/perf risk (e.g. unbatched update over a huge table), else `architecture` `minor`.
- **Unbatched data migration over a large table.** A `RunPython` doing `Model.objects.update(...)` / row-by-row over an observation table → same outage risk as an in-transaction index; treat as `migration_safety` and recommend batching (`--batch-size`, `WHERE new_id IS NULL` resumability) per the repo's heavy-migration docs. Often `major`/`blocker` depending on table size.

## SKIP_MIGRATIONS context

Heavy migrations in this repo are gated at deploy time with `SKIP_MIGRATIONS=1` and run manually (detached `tmux`/`screen`, or raw SQL + `--fake`). You don't enforce deploy mechanics in a code review, but if a PR adds a clearly heavy migration with no mention of this in the PR body, a `minor` note ("esta migración es pesada; coordina el `SKIP_MIGRATIONS` / corrida manual al desplegar") is reasonable — not blocking.
